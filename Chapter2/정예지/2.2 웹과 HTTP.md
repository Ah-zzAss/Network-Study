# 2.2 웹과 HTTP

새로운 애플리케이션인 월드와이드웹의 등장으로 일반 대중의 데이터 네트워크 사용률이 높아졌다.

- 온디맨드 방식: 원할 때 원하는 것을 수신한다.
- 모든 사람이 매우 낮은 비용으로 발행자가 될 수 있다.

## 2.2.1 HTTP 개요

웹 애플리케이션 계층 프로토콜이다.
웹 클라이언트가 웹서버에게 웹페이지를 어떻게 요청하는지, 서버가 클라이언트로 어떻게 웹 페이지를 전송하는지를 정의한다.

- 브라우저: 요구한 웹 페이지를 보여주고, 여러가지 인터넷 항해와 구성 특성을 제공한다.
- 웹 서버: URL로 각각을 지정할 수 있는 웹 객체를 갖고 있다.

### 관련 용어
- 웹페이지: 기본 HTML 파일과 여러 참조 객체들로 구성된다.
- 객체: 단순히 단일 URL로 지정할 수 있는 하나의 파일이다.
- URL: 객체를 갖고 있는 서버의 호스트 이름, 객체의 경로 이름을 가진다.

### 상호작용
HTTP는 TCP를 전송 프로토콜로 사용한다.
데이터의 손실, 순서는 TCP와 프로토콜 스택의 하위 계층이 하는 일이다.

1. TCP 연결 시작 : HTTP 클라이언트가 서버에게 요청
    - 연결이 이루어지면, 브라우저/서버 프로세스는 그들의 소켓 인터페이스를 통해 TCP로 접속
2. 데이터 교환
    - HTTP 클라이언트가 요청 메세지를 소켓 인터페이스로 보내고, 소켓 인터페이스로부터 HTTP 응답 메세지를 받는다.
    - HTTP 서버는 소켓 인터페이스로부터 요청 메세지를 받고, 응답 메세지를 소켓 인터페이스로 보낸다.

## 2.2.2 비지속/지속 연결

클라이언트-서버 상호작용이 TCP 연결을 통해 발생할 때 두 방식 중 하나로 전달된다.

- **비지속 연결**: 각 요구/응답 쌍이 **분리된** TCP 연결을 통해 보내지는 것
- **지속 연결 (Http의 Defalut)**: 모든 요구/응답 쌍이 **같은** TCP 연결을 통해 보내지는 것

### 비지속 연결 HTTP

서버가 객체를 보낸 뒤 각 TCP 연결이 끊어진다.

- HTML 파일을 요청하고 수신하는데 걸리는 시간 = RTT(TCP 연결 초기화) + RTT(파일 요청) + HTML 파일을 서버가 전송하는데 걸리는 시간
    > RTT(round-trip-time): 작은 패킷이 클라이언트로부터 서버로 가고, 다시 클라이언트로 돌아오는 시간

1. 클라이언트는 특정 포트로 TCP 연결을 시도한다. 
    -> TCP 연결과 관련하여 클라이언트, 서버에 각각 소켓이 존재하게 된다.
2. 클라이언트는 TCP 연결 소켓을 통해 서버로 HTTP 요청 메세지를 보낸다.
    요청 메세지에는 경로 이름이 포함된다.
3. 서버는 TCP 연결 소켓을 통해 요청 메세지를 받는다.
    저장 장치로부터 경로 객체를 추출하고, HTTP 메세지에 그 객체를 캡슐화 한다.
4.  서버는 응답 메세지를 소켓을 통해 클라이언트로 보낸다.
5. 서버는 TCP에게 TCP 연결을 끊으라고 한다. 
    (클라이언트가 응답 메세지를 받아야 끊긴다.)
6. 클라이언트가 응답 메세지를 받으면 TCP 연결이 중단된다.
7. 클라이언트는 응답 메세지로부터 파일을 추출하고, HTML 파일을 조사하고, 객체에 대한 참조를 갖는다.
8. 그이후에 참조되는 각 객체에 대해 연결부터 다시 반복한다.

- **단점**:
    - 각 요청 객체에 대한 새로운 연결이 설정, 유지되어야한다.
    - TCP 버퍼가 할당되어야하고, TCP 변수들이 클라이언트/서버 양쪽 모두 유지되어야한다.

### 지속 연결 HTTP

서버는 응답을 보낸 후 TCP 연결을 그대로 유지한다.

- 파이프라이닝(Defalut모드): 객체에 대한 요구는 진행 중인 요구에 대한 웅답을 기다리지 않고 연속해서 만들어질 수 있다.

## 2.2.3 HTTP 메세지 포멧

### HTTP 요청 메세지
클라이언트가 서버에 자원을 요청할 때 보내는 메시지이다.
요청라인(Method, URL, Version), 헤더, 본문(Body)으로 구성된다.

### HTTP 응답 메세지
서버가 클라이언트의 요청에 대한 결과를 전달할 때 보내는 메시지이다.
상태라인(Version, Status Code), 헤더, 본문(Body)으로 구성된다.

## 2.2.4 사용자와 서버 간의 상호작용: 쿠키

- 기능: 사이트가 사용자를 추적하게 해준다.
- 등장 배경: 비상태 HTTP 위에서 사용자 세션 계층 생성

### 쿠키의 요소

1. HTTP 응답 메세지 쿠키 헤더 라인
2. HTTP 요청 메세지 쿠키 헤더 라인
3. 사용자 브라우저에 사용자 종단 시스템과 관리를 지속시키는 쿠키 파일
4. 웹사이트의 백엔드 데이터베이스

### 쿠키 동작 방식

**[유저가 처음 브라우저에 접속]**
1. 웹서버는 유일한 식별번호를 만든다.
2. 웹서버는 식별번호로 인덱싱되는 백엔드 데이터베이스 안에 엔트리를 만든다.
3. 서버는 `Set-Cookie:식별번호` 헤더가 포함되는 HTTP 응답을 유저의 브라우저로 응답한다.

**[유저가 다시 브라우저에 웹페이지 요청]**
1. 브라우저는 유저의 쿠키 파일을 참조
2. 사이트에 대한 식별번호를 발췌
3. HTTP 요청에 식별번호를 포함하는 쿠키 헤더 파일을 넣는다.

## 2.2.5 웹 캐시 (Web Cache, Proxy Server)

웹 서버를 대신하여 HTTP 요구를 충족시키는 네트워크 개체이다.  
자체의 저장 디스크를 갖고 있어 최근 호출된 객체의 사본을 저장 및 보존한다.

- 캐시는 서버이면서 클라이언트이다.
- 일반적으로 ISP(인터넷 서비스 제공업체)가 구입하고 설치한다. 

### 동작 방식

브라우저는 사용자의 모든 HTTP 요구가 웹 캐시에 가장 먼저 보내지도록 구성될 수 있다.

1. 브라우저는 웹 캐시와 TCP 연결을 설정하고, 웹 캐시에 있는 객체에 대한 HTTP 요청을 보낸다.
2. 웹 캐시는 객체의 사본이 자기에게 저장되어 있는지 확인한다.
3. 있으면-> 웹 캐시는 클라이언트 브라우저로 HTTP 응답 메세지와 함께 객체를 전송
4. 없으면: 
    - 기점 서버인 TCP 연결을 설정
    - 웹 캐시는 캐시와 서버 간의 TCP 연결로 객체에 대한 HTTP 요청을 보낸다. 
    - 요청을 받은 후, 기점 서버는 웹 캐시로 HTTP 응답 메세지와 함께 객체를 보낸다.
3. 웹 캐시의 객체를 수신할 때, 객체를 지역 저장 장치에 복사하고 클라이언트 브라우저에 HTTP 응답 메세지와 함께 사본을 보낸다

### 특징

- 클라이언트의 요구에 대한 응답 시간을 줄일 수 있다.
- 한 기관에서 인터넷으로의 접속하는 링크상의 웹 트래픽을 대폭 줄일 수 있다.

### 조건부 GET

캐시 내부에 있는 객체의 복사본이 새것이 아닐 수도 있다.
HTTP는 클라이언트가 브라우저로 전달되는 **모든 객체가 최신의 것임을 확인하면서 캐싱**해주는 방식 '**조건부 GET**'을 갖고 있다.

- 다음 조건을 만족하면 '조건부 GET 메세지'이다.
    1. HTTP 요청 메세지가 GET를 사용
    2. Modified-Since: 헤더라인을 포함

#### 동작 방식

조건부 GET은 **서버에게** 그 객체가 명시된 날짜 이후 **수정된 경우에만** 그 객체를 **보낼 것**을 명시한다.

1. 웹 브라우저의 요청을 대신해 프록시 캐시는 요청 메세지를 웹 서버로 보낸다.
2. 웹 서버는 캐시에게 객체를 가진 응답 메세지를 보낸다.
3. 캐시는 요청하는 브라우저에게 객체를 보내주고 자신에게도 객체를 저장하는데, 이 때 **마지막으로 수정된 날짜 `Modified-Since`**를 함께 저장한다.
4. 일주일 후에 다른 브라우저가 같은 객체를 캐시에게 요청하면 객체는 여전히 저장되어 있다.
5. 해당 객체는 지난주에 웹 서버에서 수정된 상태이다 -> 브라우저는 조건부 GET으로 갱신 조사를 수행한다.
6. **`Id-modified-since` 헤더 라인**의 값이 일주일 전에 서버가 보낸 **마지막으로 수정된 날짜 `Modified-Since`** 헤더라인의 값과 정확히 일치한다 (최신 객체라는 의미)
7. 웹서버는 클라이언트에게 응답 메세지를 보낸다.
    단, 응답 메세지는 요청된 객체를 포함하지 않는다.
    응답 메세지는 304 Not Modified 상태 라인을 갖고 있으며, 이는 클라이언트에게 요청 객체의 캐싱된 복사본을 사용하라는 것을 의미한다.

## 2.2.6 HTTP/2

**주요 목표**: 하나의 연결 상에서 멀티플렉싱 요청/응답 지연 감소
**제공 기능**: 요청 우선순위화, 서버 푸시, HTTP 헤더 필드의 효율적인 압축 기능 등
**변경점**: 클라이언트-서버 간의 데이터 포맷 방법과 전송 방법

### HOL 블로킹
HTTP/1.1은 지속적인 TCP 연결을 이용하여 **하나의 TCP 연결상에서** 서버로부터 클라이언트로 보내지는 웹페이지를 허용한다.

하나의 TCP 상에서 웹 페이지에 있는 모든 객체를 보내면 HOL(Head Of Line) 블로킹 문제가 발생할 수 있다.

- 예시: 하나의 TCP 연결로 비디오 클립, 작은 객체들을 보내려고 함 -> 비디오 클립은 병목 링크를 통과하는데 오랜 시간이 걸림-> 작은 객체들을 블로킹하게 된다.
- HTTP/1.1은 여러 개의 병렬 TCP 를 열어서 문제 해결해왔음.
    -> 이 문제의 단점이 브라우저는 일종의 속임수로 링크 대역폭의 많은 부분을 받게 된다.
- HTTP/2는 **프레이밍**을 통해 병렬 TCP를 줄이거나 제거하고자 함

### HTTP/2 프레이밍

각 HTTP 메세지를 독립된 프레임들로 쪼개고, 인터리빙하고, 하나의 지속적인 TCP 연결 상에서 전송된다.
프레임들은 반대편 사이트에서 재조립한다.

- 프레이밍은 HTTP/2 프로토콜의 프레임으로 구현된 다른 프레이밍 서브 계층에 의해 이루어진다. 
- 프레이밍 서브 계층은 프레임을 바이너리 인코딩 하기도 한다. 이는 파싱하기 더 효율적, 좀 더 작은 프레임 크기를 갖고, 에러에 더 강하다.

### 메세지 우선순위화

클라이언트가 하나의 특정 서버로 동시에 여러 개의 요청을 할 때,  
**각 메세지에 1-256의 가중치**를 부여함으로써 **요청에 우선순위**를 매길 수 있다.
- 높은 수치일수록 높은 우선순위를 의미한다.
- 가장 높은 우선 순위의 요청을 위한 프레임을 제일 먼저 보낼 수 있다.

### 서버 푸싱

처음 요청에 대한 응답 외에, **서버는 클라이언트의 요청 없이도 추가적인 객체를 클라이언트에게 푸시하여 보낼 수 있다.**

- **동작**: 객체에 대한 HTTP 요청을 기다리는 대신, 서버는 HTML 페이지 분석, 필요 객체 식별, 요청이 도착하기도 전에 해당 객체들을 클라이언트로 보낼 수 있음.
- **효과**: 해당 요청을 기다리는데 소요되는 추가 지연을 없앰
- **가능한 이유**: HTML 기반 페이지가 웹페이지를 완벽하게 구동시킬 필요가 있는 객체들을 가리킬 수 있음

### HTTP/3

새로운 트랜스 프로토콜인 QUIC 위에서 작동하도록 설계된 새로운 HTTP 프로토콜  
아직 표준화된 상태는 아니다.

- **QUIC**: UDP 프로토콜 위에 위치하는 애플리케이션 계층에 구현되어 있음
- 메세지 멀티플랙싱(인터리빙), 스트림별 흐름 제어, 저지연 연결 확립 등 여러 특징을 가짐
