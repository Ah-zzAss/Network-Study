# 네트워크 애플리케이션의 원리

### 네트워크 애플리케이션 구조

네트워크 구조는 5계층으로 고정되어 있고, 애플리케이션 구조는 두 가지의 잘 알려진 구조가 있다.

1. 클라이언트-서버 구조
    
    웹, 파일 전송, 원격 로그인, 전자메일 등
    
    1. 서버 
        1. 항상 동작하고 있는 호스트
        2. 클라이언트 호스트로부터 객체를 요청받으면 요청된 객체를 보내면서 응답
        3. 고정 ip 주소
        4. 많은 요청을 처리하기 위해 많은 수의 호스트를 갖춘 데이터 센터가 존재한다.
    2. 클라이언트
        1. 가끔 또는 항상 켜져있는 호스트
        2. 서버로 서비스를 요청
        3. 클라이언트는 서로 직접적으로 통신하지 않는다.

1. P2P  구조
    
    항상 켜져있는 서버에 최소로 의존한다.
    
    대신 사용자들의 테스크탑, 랩톱 등이 피어가 되어서 서로 직접 통신하게 된다.
    
    자가 확장성 : 각 피어들이 파일을 요구함으로써 작업 부하가 일어나지만 또한 파일을 다른 피어들에게 분배함으로써 서비스 능력을 추가한다.
    

### 프로세스 간 통신

실제 통신하는 것은 프로그램이 아닌 프로세스다.

각 종단 시스템에서 프로세스는 네트워크를 통한 메시지 교환으로 서로 통신한다.

두 프로세스 간의 통신 세션에서 통신을 초기화하는 프로세스를 클라이언트라 하고, 세션을 시작하기 위해 접속을 기다리는 프로세스를 서버라고 한다.

프로세스는 소켓을 통해 네트워크로 메세지를 보내고 받는다.

소켓은 애플리케이션 계층과 트랜스포트 계층 간의 인터페이스이고 애플리케이션과 네트워크 사이의 API라고도 한다.

다른 호스트의 프로세스에게 패킷을 보내기 위해서 호스트의 주소(IP)와 수신 프로세스를 명시하는 식별자(포트 번호)가 필요하다.

### 애플리케이션이 이용 가능한 트랜스포트 서비스

메시지를 주고 받을 때 트랜스포트 계층 프로토콜을 하나 선택해야 한다.

트랜스포트 계층 프로토콜은 신뢰적 데이터 전속, 처리율, 시간, 보안이라는 네 가지 차원에서 고려해서 선택한다.

1. 신뢰적 데이터 전송
    
    데이터 전송을 손실없이 보장한다면 신뢰적 데이터 전송, 손실을 허용한다면 손실 허용 애플리케이션
    
2. 처리율
    
    처리율 : 비트를 전송하는 속도 
    
    대역폭 민감 애플리케이션 : 최소한으로 보장해야하는 처리율을 가진 애플리케이션
    
    탄력적 애플리케이션 : 보장해야하는 처리율이 없는 애플리케이션
    
3. 시간
    
    비트가 도착하는 시간
    
4. 보안
    
    트랜스포트 프로토콜은 애플리케이션에 하나 이상의 보안 서비스를 제공할 수 있다.
    

### 인터넷 전송 프로토콜이 제공하는 서비스

1. TCP 서비스
    1. 연결 지향형 : 핸드셰이킹 과정으로 통해 연결
    2. 신뢰적인 데이터 전송 서비스
    3. 혼잡 제어 방식 : 통신하는 프로세스의 직접 이득보다 인터넷 전체 성능 향상
    4. TLS 보안 (나중에 8장에서 나옴)
2. UDP 서비스
    1. 비연결형, 핸드셰이킹X
    2. 비신뢰적인 데이터 전송 서비스 : 데이터가 손실 날 수도 있고 순서가 바뀔수도 있다.
    3. 혼잡 제어 방식 X, 데이터를 원하는 속도로 보낼 수 있다.

전자메일, 원격 터미널 접속, 웹, 파일 전송 등은 TCP를 사용하고 있다. TCP가 모든 데이터가 도착하도록 보장하는 신뢰적 데이터 전송 서비스를 제공하기 때문이다.

인터넷 전화는 보통 패킷 손실을 허용하지만 최소의 전송률을 필요로 하기 때문에 일반적으로 UDP를 사용한다. 많은 방화벽이 UDP 트래픽을 차단하기 때문에 UDP 통신이 실패할 경우 TCP를 사용하도록 되어있다.

### 애플리케이션 계층 프로토콜

다른 종단 시스템에서 실행되는 애플리케이션의 프로세스가 서로 메시지를 보내는 방법을 정의

- 교환 메시지 타입
- 여러 메시지 타입의 문법
- 필드의 의미 등등

네트워크 애플리케이션(앱)과 애플리케이션 계층 프로토콜을 구별하는 것이 중요

애플리케이션 계층 프로토콜은 앱의 한 요소일 뿐이다.

예를 들어서 웹 애플리케이션은 HTML, 웹 브라우저, 웹 서버, 애플리케이션 계층 프로토콜로 구성된다. 여기서 애플리케이션 계층 프로토콜(HTTP)는 메시지의 포맷과 순서를 정의한다.
따라서 HTTP는 단지 웹 애플리케이션의 한 요소이다.

# 웹과 HTTP

### HTTP 개요

웹의 애플리케이션 계층 프로토콜인 HTTP는 웹의 중심이다.

[RFC 1945], [RFC 7230], [RFC 7540]에 정의되어 있고 클라이언트, 서버 프로그램으로 구현된다.

HTTP는 메시지의 구조 및 클라이언트와 서버가 어떻게 메시지를 교환하는지 정의하고 있다.

브라우저가 요청하고 서버가 요청을 수신하여 객체를 포함한 응답 메시지로 응답하는 형식이다.

HTTP는 데이터의 손실 또는 TCP가 어떻게 손실 데이터를 복구하고 처리하는지는 걱정할 필요가 없다. 이것은 TCP와 프로토콜 스택의 하위 계층들이 하는 일이고 메시지가 소켓을 통해 전송하는 것이 HTTP의 역할이다.

서버는 클라이언트에 대한 정보를 유지하지 않으므로 HTTP를 비상태 프로토콜이라고 한다.

### 비지속 연결과 지속 연결

1. 비지속 연결
    
    각 요구/응답 쌍이 분리된 TCP 연결로 보내지는 것
    
    연결 수행 과정은 다음과 같다.
    
    1. 클라이언트가 기본 포트 80을 통해 TCP 연결을 시도
    2. 클라이언트가 TCP 연결 소켓을 통해 HTTP 요청 메시지를 보냄
    3. 서버가 TCP 연결 소켓을 통해 메시지를 받음
    4. 저장장치에서 요청 객체를 추출하고 TCP 연결 소켓을 통해 클라이언트에게 보냄
    5. 서버가 TCP 연결을 끊으라고 함 (실제로는 클라이언트가 응답 메시지를 받을 때 까지 연결을 끊지 않는다)
    6. 클라이언트가 응답 메시지를 받으면 TCP 연결이 중단된다.
    7. 그 이후에 참조되는 각 객체에 대해 반복한다.
    
2. 지속 연결
    
    각 요구/응답 쌍이 같은 TCP 연결로 보내지는 것

### 2.2.3 HTTP 메시지 포맷

```markdown
GET /somedir/page.html HTTP/1.1
Host: www.somecschool.edu
Connection: close
User-agent: Mozilla/5.0
Accept-language
```

위는 HTTP 요청 메시지 예시이다.

1. 메시지가 일반 ASCII 텍스트로 쓰여 있어 사람들이 읽을 수 있다.
2. 메시지가 다섯 줄로 되어있고 각 줄은 CR과 LF로 구별된다. 마지막 줄에 이어서 추가 CR과 LF가 따른다.
3. 첫 줄은 요청 라인, 이후의 줄들은 헤더 라인이라고 부른다.
4. 요청 라인은 방식(method),  URL, HTTP 필드가 존재한다.
5. Connection : close를 통해 지속 연결 사용을 원하지 않는다는 것을 말하고 있다.
6. User-agent: 헤더라인은 서버에게 요청을 하는 브라우저 타입을 명시
7. Accept-language: 사용자의 언어, 이것이 존재하지 않으면 기본 버전을 보낸다
8. 위의 일반 포맷 이후 entity body가 있다. entity body는 GET 방식에서는 비어있고 POST 방식에서 사용된다. 사용자가 폼 필드에 입력한 것을 entity body에 포함한다.

```markdown
HTTP/1.1 200 OK
Connection: close
Date: Tue, 18 Aug 2015 15:44:04 GMT
Server: Apache/2.2.3 (CentOS)
Last-Modified: Tue, 18 Aug 2015 15:11:03 GMT
Content-Length: 6821
Content-Type: text/html

데이터.....
```

위는 HTTP 응답 메시지 예시이다.

1. 상태 라인(statue line), 6개의 헤더 라인, 개체 몸체(entity body)로 이루어졌다.
2. 상태 라인은 프로토콜 버전 필드, 상태 코드, 해당 상태 메시지의 3개의 필드로 이루어져있다.
3. Connetion: close : 클라이언트에게 메시지를 보낸 후 TCP 연결을 닫는다. 
4. Date : HTTP 응답이 생성되고 보낸 날짜와 시간
5. Server : 메시지가 어떤 서버로 만들어졌는지 나타냄. 요청 메시지의 user-agent 헤더라인과 비슷
6. Last-Modified : 객체가 생성되거나 마지막으로 수정된 시간과 날짜
7. Content-Length : 송신되는 객체의 바이트 수
8. Content-Type : 개체 몸체(entity body) 내부의 객체가 HTML 텍스트인 것을 나타낸다.

상태 코드는 여러가지가 있다.

200 OK : 요청 성공, 정보가 응답함.

301 Moved Permanently : 요청 객체가 영원히 이동되었다.

### 쿠키

HTTP 서버는 상태를 유지하지 않지만, 사용자를 확인하기 위해 쿠키를 사용한다. 

쿠키는 네 가지 요소가 있다.

1. HTTP 응답 메시지 쿠키 헤더 라인
2. HTTP 요청 메시지 쿠키 헤더 라인
3. 사용자 종단 시스템에 쿠키파일
4. 웹사이트의 백엔드 데이터 베이스

 

![image.png](attachment:b926f8f9-c7ff-43bb-83cb-94a3a9f26c85:image.png)

쿠키의 작동 원리는 위와 같다.

1. 사용자가 이전에 이베이에 방문한 적이 있고, 아마존에 처음 방문을 시도한다.
2. 아마존 웹 서버에 요청이 들어오면 서버는 식별번호를 만들어서 백엔드 데이터베이스에 엔트리를 만들고 식별번호를 HTTP 응답(Set-cookie: 1678)에 포함한다.
3. 사용자가 HTTP 응답 메시지를 받았을 때 쿠키 파일에 서버 호스트 이름과 식별번호를 푸가한다.
4. 이후 사용자가 웹 페이지에 요청을 보낼 때 사용자 브라우저는 쿠키 파일을 참조하여 접속하는 사이트에 대한 식별번호를 가져와서 쿠키 헤더에 포함하여 HTTP 요청을 보낸다.
5. 일주일 후에 접속하더라도 cookie: 1678이라는 식별번호를 통하여 사용자를 식별하고 적합한 데이터를 보낸다.

### 웹 캐싱

웹 캐시는 프록시 서버라고도 한다. 웹 서버를 대신하여 HTTP 요구를 충족시키는 네트워크 개체.

웹 캐시는 자체 저장 디스크를 갖고 있어 최근 호출된 객체의 사본을 저장 및 보존한다.

브라우저들은 기점 서버로 요청을 보내기 전에 웹 캐시로 먼저 요청을 보내고 해당 객체가 있을 경우 빠르게 받을 수 있고 없을 경우 웹 캐시가 클라이언트가 되어 기점 서버로 객체를 요청한다.

![image.png](attachment:f931b8f9-8826-486d-a2a0-a81b636f764d:image.png)

네트워크 구성이 아래와 같을 때 기관 라우터에서 공중 인터넷 라우터에 높은 트래픽 강도가 생긴다. 

웹 캐시를 설치하여 적중률이 0.4라고 하면 요청의 40%가 웹 캐시가 처리하여 트래픽 강도가 대폭 낮아진다.

![image.png](attachment:531c0cbb-ef2b-4215-9673-94ec8db1a441:image.png)

문제는 웹 캐시에 있는 복사본이 새 것이 아닐 수 있다. 캐싱된 이후 서버에 있는 객체가 갱신되었을 수도 있다.

최신임을 확인하기 위해 조건부 GET 방식을 사용한다.

객체가 캐시에 저장될 때 수정된 날짜를 함께 저장하고 이후 다시 요청을 보낼 때 If- modified-since 헤더라인을 통해 객체가 그 이후 갱신되었을 경우 객체를 보내고 변경되지 않았을 경우 객체를 포함하지 않고 응답 메시지를 보낸다.

### HTTP/2

HTTP/2의 주요 목표는 하나의 TCP 연결상에서 멀티플렉싱 요청/응답 지연시간을 줄이는 데 있어 요청 우선순위화, 서버푸시, HTTP 헤더필드의 효율적이 압축 기능 등을 제공한다.

상태코드, URL, 헤더필등 등 HTTP 메소드 자체는 변경하지 않고, 데이터 포맷 방법, 전송 방법을 변경했다.

HOL 블로킹 문제를 해결하기 위해 HTTP/1.1 브라우저는 여러 개의 병렬 TCP 연결을 열어서 문제를 해결했다. 

HTTP/2의 주요 목표 중 하나는 병렬 TCP 연결의 수를 줄이거나 제거하여 필요한 소켓 수를 줄이고 TCP 혼잡 제어를 제어할 수 있게 하는데 있다.

1. 프레이밍
    
    각 메시지를 작은 프레임으로 나누고 같은 TCP 연결에서 용청 응답 메시지를 인터리빙한다.
    
    1000프레임의 비디오 클립과 2프레임의 8개의 객체가 있다면 기존 방식으로는 1016 개의 프레임이 보낸 후에야 작은 객체가 전송 완료되지만 프레이밍을 통해 하나씩 보낸다면 18개의 프레임이 보내면 작은 객체들이 전부 보내진다.
    
    프레이밍은 다른 프레이밍 서브 계층에 의해 이루어진다.
    
2. 메시지 우선순위화 및 서버 푸싱
    
    개발자가 요청들의 상대적 우선 순위를 조정한다. 1~256(높을 수록 높은 우선순위)
    
    클라이언트 요청에 대해 여러 개의 응답을 보낼 수도 있다. HTTP 요청을 기다리는 대신 필요한 객체들을 요청이 도착하기 전에 보낸다.
    
3. HTTP/3
    
    트랜스포트 프로토콜인 QUIC를 통해 훨씬 더 간단한 설계가 가능하지만 현재 표준화 상태는 아니다.
    

# 인터넷 전자메일

전자메일은 인터넷 시작한 이래로 가장 중요하고 널리 사용되는 애플리케이션 중 하나다.

인터넷 메일 시스템에는 사용자 에이전트, 메일 서버, SMTP 3개의 주요 요소가 있다.

사용자 에이전트 : 사용자가 메시지를 읽고 응답하고 전달하고 저장하고 구성한다.

메일 박스 : 수신자에게 온 메일을 유지하고 관리하는 박스

SMTP : 인터넷 전자메일을 위한 주요 애플리케이션 계층 프로토콜

<img width="666" height="774" alt="image" src="https://github.com/user-attachments/assets/7017dec8-ab37-4e38-bf8a-1aa387e655e8" />

### SMTP

<img width="1230" height="312" alt="image" src="https://github.com/user-attachments/assets/ae560331-88e6-4320-aacd-efeb152b6a8a" />


1. 앨리스가 밥의 메일 주소와 메시지를 작성하고 사용자 에이전트에게 메시지를 보내라고 명령한다.
2. 사용자 에이전트는 메시지를 앨리스의 메일 서버로 보내고 메시지 큐에 놓인다.
3. 앨리스의 메일서버(SMTP 클라이언트)는 밥의 메일서버(SMTP 서버)애개 TCP연결을 설정한다.
4. 핸드셰이킹 이후 앨리스의 메시지를 TCP 연결로 보낸다.
5. 밥의 메일 서버를 메시지를 수신하고 메일 박스에 놓는다.
6. 밥이 편한 시간에 메시지를 읽기 위해 사용자 에이전트를 시동한다.

두 사람이 멀리 떨어져 있어도 중간 메일서버가 없고 밥의 메일 서버가 죽어있다면 메일은 앨리스 메잇 서버에 남아 계속 시도한다.

### 메일 메시지 포맷

메시지 몸체 앞에 주변 정보가 포함된 헤더가 RFC 5322에 정의되어 있다. 

필수값으로는 From:, To:가 있고 Subject:는 선택사항이다.

SMTP 명령과 공통 단어가 있지만 SMTP는 핸드셰이킹 프로토코르이 일부이고 RFC 5322는 메시지 자체의 일부이다.

### 메일 접속 프로토콜

SMTP는 push 프로토콜이라서 수신자의 사용자 에이전트에서 자신의 메일 서버에 있는 메일을 가져오는(pull) 동작을 할 수 없다.

HTTP나 IMAP을 통해 메일 서버에 접근할 수 있다.

# DNS

인터넷 호스트를 식별하는 것은 두가지가 있다.

“naver.com”과 같은 호스트 이름과, 121.7.106.83과 같은 ip주소이다.

사람은 더 기억하기 쉬운 호스트 이름을 선호하지만, 라우터는 ip주소를 선호한다.

그래서 호스트 이름을 ip 주소로 변환해주는 디렉터리 서비스가 필요한데 이것이 인터넷 DNS의 주요임무이다.

1. DNS 서버들의 계층구조로 구현된 분산 데이터베이스이고
2. 호스트가 분산 데이터베이스로 질의하도록 허락하는 애플리케이션 계층 프로토콜이다.

DNS는 호스트 이름을 IP 주소로 변환하는 것 외에 추가 서비스를 제공한다.

1. 호스트 에일리어싱 : 복잡한 호스트 이름의 경우 별칭을 가질 수 있는데 별칭 호스트 이름을 정식 호스트 이름으로 변환해준다.
2. 메일 서버 에일리어싱 : 전자메일 주소의 경우도 더 복잡하다. 그래서 정식 메일서버 호스트 이름으로 변환해준다.
3. 부하 분산 : 대형 사이트의 경우 여러 서버에 중복되어 있다. 하나의 정식 호스트 이름과 연관되어 여러 IP 주소를 가지고 있는데, 클라이언트가 해당 호스트 이름으로 DNS 질의를 하면 순환식으로 주소를 제공하여 트래픽을 분산하는 효과를 낸다.

### DNS 동작 원리

DNS를 간단하게 하나의 서버로 중앙 집중 방식이라면 많은 문제가 생긴다.

서버가 고장, 트래픽양, 유지관리 등등..

그래서 분산 계층 데이터 베이스를 사용한다.

<img width="704" height="244" alt="image" src="https://github.com/user-attachments/assets/2f40c195-d72d-4e32-a975-1cd97b543d03" />

1. 루트 DNS 서버 :  전 세계의 13개의 루트 서버 복사체들이 존재한다. TLD 서버의 IP 주소들을 제공한다.
2. 최상위 레벨 도메인 서버 : TLD는 com, org, net, edu, gov 같은 상위 레벨 도메인과 국가 레벨 도메인 서버이다. 책임 DNS 서버의 IP 주소들을 제공한다.
3. 책임 DNS 서버 : 특정 호스트 이름의 최종 IP 주소를 보관하고 있는 장소

<img width="952" height="1038" alt="image" src="https://github.com/user-attachments/assets/ce903439-da8f-417f-b29d-7e5d636480bf" />

1. 호스트가 로컬 DNS 서버에게 요청을 보낸다. 알아야 하는 호스트 이름(gaia.cs.umass.edu)를 포함한다.
2. 로컬 DNS는 루트 DNS서버에게 요청을 보낸다.
3. 루트 DNS는 edu를 인식하여 edu에 대한 TLD DNS 서버 IP 주소를 보낸다.
4. 로컬 DNS는 TLD DNS 서버에게 요청을 보낸다.
5. TLD DNS 서버는 umass.edu를 인식하여 관련있는 책임 DNS 서버 IP 주소를 보낸다.
6. 로컬 DNS는 책임 DNS 서버에게 요청을 보낸다.
7. 최종 ip 주소를 로컬 DNS 서버로 보낸다.
8. 로컬 DNS 서버는 최종 ip주소를 호스트에게 전달한다.

하나의 이름 매핑을 얻기 위해 총 8번의 DNS 메시지가 보내진다.
