# 3.5 연결지향형 트랜스포트: TCP

## 3.5.1 TCP 연결
한 호스트에서 동작하는 프로세스(클라이언트 프로세스)가 다른 호스트(서버 프로세스)와 연결을 초기화하기를 원하는 상황입니다.

1. **3-way handshake를 진행한다.**
    1. 클라이언트가 서버로 TCP SYN 세그먼트를 보낸다.
    2. 서버는 클라이언트에게 TCP SYNACK 세그먼트를 보낸다.
    3. 클라이언트가 다시 서버로 확인 응답(ACK) 세그먼트를 보낸다.
2. 이제 연결이 설정되었으므로, 두 애플리케이션 프로세스는 서로 데이터를 보낼 수 있다.
3. 클라이언트 프로세스는 소켓을 통해 데이터 스트림을 전달한다.
4. 데이터는 클라이언트에서 동작하는 TCP가 받아서 **송신 버퍼**로 보낸다.
    * **송신 버퍼:** 3-way handshake 동안 할당되고 준비되는 메모리 공간.
    * TCP는 때때로 이 버퍼에서 데이터 묶음을 만들어 네트워크로 보낸다.
    * 세그먼트로 모아 담을 수 있는 최대 데이터의 양은 **MSS(Maximum Segment Size)**로 제한된다.
    * MSS는 일반적으로 로컬 송신 호스트가 전송할 수 있는 가장 큰 링크 계층 프레임의 길이인 **MTU(최대 전송 단위)**에 의해 결정된다.
    * MSS는 세그먼트 내 '데이터 필드'의 최대 크기를 의미한다. (헤더 제외)
5. **큰 파일의 전송:** 파일을 MSS 크기로 분절한다. 이후 TCP 세그먼트(TCP 헤더 + 데이터)와 IP 헤더 길이가 단일 링크 계층 프레임에 딱 맞도록 정해진다.

* TCP가 상대방으로부터 세그먼트를 수신하면, 그 데이터는 TCP 연결의 **수신 버퍼**에 위치한다. 애플리케이션은 필요할 때 이 버퍼로부터 데이터 스트림을 읽는다.
* 결론적으로 TCP 연결의 양 끝단은 각각 자신만의 송신 버퍼와 수신 버퍼를 가지고 양방향 통신을 한다.

## 3.5.2 TCP 세그먼트 구조
TCP 세그먼트는 **[헤더 필드] + [데이터 필드]**로 구성되어 있다.

#### UDP와 공통적으로 갖는 필드
* **출발지/목적지 포트 번호:** 상위 계층 애플리케이션으로의 다중화 및 역다중화에 사용됨.
* **체크섬(Checksum) 필드:** 데이터 오류 검출.

#### UDP와 공통적으로 갖지 않는 필드
* **32비트 순서 번호(Sequence Number) / 32비트 확인 응답 번호(ACK Number) 필드:** 신뢰적인 데이터 전송 서비스 구현에 핵심적으로 사용됨.
* **16비트 수신 윈도(Receive Window):** 흐름 제어에 사용. 수신자가 현재 받아들일 수 있는 버퍼의 여유 공간(바이트 크기)을 나타냄.
* **4비트 헤더 길이 필드:** 32비트 워드 단위로 TCP 헤더의 길이를 나타냄. (옵션 필드 때문에 가변적일 수 있음)
* **옵션 필드:** 선택적이고 가변적인 추가 정보.
* **플래그(Flag) 필드 (6비트):** SYN, ACK, FIN, RST, PSH, URG 등의 제어 비트. 연결 설정/종료, 확인 응답 필드의 유효성, 데이터 푸시 요청 등을 나타냄.

#### 32비트 순서 번호 / 확인 응답 번호 필드
* TCP에서 데이터는 구조화되어 있지 않고, 단지 순서대로 정렬된 **바이트 스트림**으로 간주한다.
* TCP는 **누적 확인 응답(Cumulative ACK)**을 제공한다. 수신자는 '첫 번째로 잃어버린 바이트의 바로 앞'까지만 확인 응답을 보낸다.
* **순서가 바뀐 세그먼트를 수신할 때 호스트의 행동:**
    * *선택지 1:* 순서가 바뀐 세그먼트를 즉시 버린다.
    * *선택지 2:* 버퍼에 임시로 보관하고, 빈 공간(잃어버린 데이터)이 채워지기를 기다린다. $\rightarrow$ 네트워크 대역폭 관점에서 더 효율적이므로 실제 구현에서 주로 사용하는 방법이다.

## 3.5.3 왕복 시간(RTT) 예측과 타임아웃
TCP는 손실된 세그먼트를 발견하기 위해 타임아웃/재전송 메커니즘을 사용한다.

#### 1. 왕복 시간 (RTT) 예측
* **SampleRTT:** 세그먼트가 송신된 시간으로부터 그 세그먼트에 대한 긍정 응답(ACK)이 도착할 때까지의 시간. (재전송된 세그먼트는 제외하고, 한 번만 전송된 세그먼트에 대해서만 측정한다.)
* **EstimatedRTT:** 네트워크의 변동성을 줄이기 위해 이전 EstimatedRTT 값과 새로운 SampleRTT 값의 가중 평균을 사용한다. 이를 **지수적 가중 이동 평균(EWMA)**이라고 부른다.
* **DevRTT:** SampleRTT가 EstimatedRTT로부터 얼마나 벗어나 있는지 나타내는 RTT의 편차(변화율).

#### 2. 타임아웃 주기 (Timeout Interval) 설정
* TCP 타임아웃 주기가 EstimatedRTT보다 너무 작으면 불필요한 재전송이 빈번하게 발생하고, 너무 크면 패킷 손실 복구가 지연된다.
* 따라서 타임아웃 값은 EstimatedRTT에 약간의 여윳값(DevRTT 기반)을 더하여 설정하는 것을 권장한다. (`TimeoutInterval = EstimatedRTT + 4 * DevRTT`)

## 3.5.4 신뢰적인 데이터 전송
프로세스가 자신의 수신 버퍼로부터 읽은 데이터 스트림이 손상, 손실, 중복 없이 **순서가 유지된다는 것을 보장**한다.

* 타이머를 여러 개 관리하는 것은 막대한 오버헤드를 유발할 수 있으므로, TCP는 **단일 재전송 타이머**를 사용한다.

#### TCP 송신자의 주요 3가지 이벤트
1. **이벤트 1: 애플리케이션으로부터 데이터 수신**
    * TCP는 데이터를 세그먼트로 캡슐화하여 IP로 넘긴다.
    * 이때 타이머가 실행 중이 아니라면, 타이머를 시작한다.
2. **이벤트 2: 타임아웃 발생**
    * 타임아웃된 세그먼트를 재전송한다.
    * 네트워크 혼잡을 피하기 위해, 재전송 시 타이머 주기를 이전보다 **2배 긴 간격**으로 늘려 다시 시작한다.
3. **이벤트 3: 수신자로부터 ACK 수신**
    * 누적 확인 응답을 사용하므로, 새롭게 확인된 세그먼트가 있다면 송신자의 윈도우 기준점(`sendbase`)을 갱신한다.
    * 아직 확인 응답을 받지 못한 세그먼트가 남아있다면 타이머를 다시 시작한다.

#### 빠른 재전송 (Fast Retransmit)
* 누적 확인 응답은 정상적으로 도착한 세그먼트들에 대해 동일한 ACK 번호를 반복해서 보내게 만든다.
* 송신자가 **3개의 중복된 ACK**(총 4개의 동일한 ACK)를 수신하면, 타이머가 만료되기 전이라도 해당 세그먼트가 손실되었다고 판단하고 **즉시 재전송**한다.

## 3.5.5 흐름 제어 (Flow Control)
TCP 송신자가 너무 많은 데이터를 너무 빠르게 보내서 **수신자의 버퍼를 오버플로 시키는 것을 방지**하기 위해 전송 속도를 조절하는 서비스.

* 송신자는 **수신 윈도(Receive Window, rwnd)**라는 변수를 유지하여 흐름 제어를 제공한다.
* 수신자는 TCP 헤더의 수신 윈도 필드를 통해, 현재 수신 버퍼에 가용한 빈 공간이 얼마나 되는지 송신자에게 지속적으로 알려준다. (연결의 각 측은 별개의 수신 윈도를 유지한다.)
* **수신 윈도가 0일 경우 (Zero Window):**
    * 송신자는 차단되어 더 이상 정상적인 데이터를 전송할 수 없다.
    * 이 교착 상태를 해결하기 위해, 송신자는 수신 버퍼가 비었는지 확인하기 위해 주기적으로 **1바이트 데이터가 포함된 탐색 세그먼트(Zero Window Probe)**를 계속해서 전송한다.
* **UDP의 경우:** 이러한 흐름 제어 기능을 제공하지 않으므로, 수신 버퍼가 가득 차면 버퍼 오버플로가 발생하고 세그먼트가 유실된다.
