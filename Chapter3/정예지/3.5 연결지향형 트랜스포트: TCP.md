# 3.5 연결지향형 트랜스포트: TCP

## 3.5.1 TCP 연결

한 호스트에서 동작하는 프로세스(클라이언트 프로세스) 가 다른 호스트 (서버 프로세스) 와 연결을 초기화 하기를 원하는 상황

1. 3-way-handshake를 진행한다.
    1. 클라이언트가 TCP 연결 세그먼트를 보낸다.
    2. 서버는 두번째 TCP 연결 세그먼트를 보낸다.
    3. 클라이언트가 다시 TCP 보낸다.
2. 이제 연결이 설정되었으므로, 두 애플리케이션 프로세스는 서로 데이터를 보낼 수 있다.
3. 클라이언트 프로세스는 소켓을 통해 데이터 스트림을 전달한다.
4. 데이터는 클라이언트에서 동작하는 TCP가 받아서 ㅅㅇ신 버퍼로 데이터를 보낸다.
    - 송신 버퍼: 3-way-handshake 동안 준비된 버퍼 중 하나인 연결
    - 때때로 TCP는 데이터 묶음을 만들어서 네트워크로 보낸다.
    - 세그먼트로 모아 담을 수 있는 최대 데이터의 양은 MSS(maxinum segment size)로 제한된다.
    - MMS는 일반적으로 로컬 송신 호스트에 의해 전송될 수 있는 가장 큰 링크 계층 프레임의 길이 (최대 전송 단위 (MTU))에 의해 결정된다.
    - MMS는 세그먼트의 데이터 필드의 크기를 제한한다.
- 큰 파일을 전송할 때 MMS크기로 파일을 분절한다.
    - 그 후, TCP 세그먼트와 TCP/IP 헤더 길이가 단일 링크 계층 프레임에 딱 맞도록 하여 정해진다.

TCP가 상대에게 세그먼트를 수신했을때, 세그먼트의 데이터는 TCP연결의 수신 버퍼에 위치한다.
애플리케이션은 이 버퍼로부터 데이터 스트림을 읽는다.
연결의 양 끝은 각각 자신의 송신 버퍼와 수신 버퍼를 가지고 있다.

### 3.5.2 TCP 세그먼트 구조

TCP 세그먼트는 [헤더 필드] + [데이터 필드]로 구성되어 있다.

#### UDP와 공통적으로 갖는 필드
- 출발지/목적지 포트번호: 상위 계층 애플리케이션으로부터 다중화, 역다중화에 사용됨
- 체크섬 필드

#### UDP와 공통적으로 갖지 않는 필드

- 32비트 순서 번호 필드 / 32비트 확인 응답 번호 필드: 신뢰적인 데이터 전송 서비스 구현에서 전송자/수신자에 의해 사용됨
- 16비트 수신 윈도: 흐름 제어에 사용, 수신자가 받아들이려는 바이트의 크기를 나타냄
- 4비트 헤더 길이 필드: 32비트 워드 단위로 TCP 헤더 길이를 나타냄
- 옵션 필드: 선택, 가변적
- 플래그 필드: ???

####  32비트 순서 번호 필드 / 32비트 확인 응답 번호 필드

데이터는 구조화되어 있지 않고, 단지 순서대로 정렬된 바이트 스트림
TCP는 누적확인응답을 제공함: 첫번째 잃어버린 바이트까지의 바이트들까지만 확인 응답을 제공

- 순서가 바뀐 세그먼트를 수신할 때 호스트가 하는 행동: 
    선택지1: 순서가 바뀐 세그먼트를 즉시 버린다.
    선택지2: 보유하고, 빈 공간에 잃어버린 데이터를 채우기 위해 기다린다. -> 후자가 네트워크 대역폭 관점에서 효율적, 실제에서 ㅎ사용하는 방법

### 3.5.3 왕복 시간(RTT) 예측과 타임아웃

TCP는 손실 세그먼트를 발견하기 위해 타임아웃/재전송 매커니즘을 사용한다.

#### 왕복 시간 예측

- sampleRTT: 세그먼트가 송신된 시간으로부터 그 세그먼트에 대한 긍정 응답이 도착한 시간까지의 시간 길이
- 모든X, 재전송된 X, 한 번 전송한 세그먼트에 대해서만 측정한다.
- estimatedRTT 이전 값과 새로운 sampleRTT 값의 가중된 조합인 estimatedRTT를 사용한다. 이는 sampleRTT의 가중평균이다.
- 지수적 가중 이동 평균 (EWMA)라고 부른다.
- RTT 변화율인 DevRTT

#### 왕복 시간 예측
- TCP 타임아웃 주기는 estimatedRTT보다 크거나 같지 않으면 불필요한 재전송이 발송된다.
- 타임아웃값은 estimatedRTT에 약간의 여윳값이 더해진 값으로 설정되는 ㅓㄱㅅ을 권유한다.

### 3.5.4 신뢰적인 데이터 전송

프로세스가 자신의 수신 버퍼로부터 읽은 데이터 스트림이 손상되지 않았으며, 손실이나 중복 없이 순서가 유지된다는 것을 보장한다.

- 타이머 관리는 오버헤드를 유발할 수 있다. 따라서 단일 타이머를 따른다.

TCP 송신ㅈ의 데이터 전송/재전송에 관련된 세가지 주요 이벤트
1. 첫번째 주요 이벤트: 수신된 데이터
    - TCP는 애플리케이션으로부터 데이터를 받고, 세그먼트로 그 데이터를 캡슐화하고, IP에게 이 세그먼트를 넘긴다.
    - 넘길 때 타이머를 시작한다.
2. 두번째 주요 이벤트: 타임 아웃
    - 타임아웃 이벤트에 대해 세그먼트를 재전송하여 응답한다.
    - 그 후 다시 타이머를 시작한다.
3. 세번째 주요 이벤트: 수신자로부터 수신 확인응답 세그먼트
    - 누적 확인 응답을 사용하므로 이전에 확인 응답 안된 하나 이상의 세그먼트를 확인 후 자신의 sendbase변수를 갱신
    - 아직 확인 응답 안된 세그먼트가 존재한다면 타이머를 다시 시작

- 누적 확인 응답은 첫번째 세그먼트의 재전송을 방지한다.
- 혼잡할 때 재전송을 고집하면 악화될 것이므로 송신자가 더 긴간격으로 재전송 하도록 한다.
- 세그먼트의 타이머가 초과되기 이전에 손실된 새그먼트를 재전송하는 빠른 재전송을 한다. 

### 3.5.5 흐름 제어

흐름제어 서비스: TCP가 송신자가 수신자의 버퍼를 오버플로 시키는 것을 방지하기 위해 속도를 일치시키는 서비스

- 송신자가 수신 윈도라는 변수를 유지하여 흐름 제어를 제공
- 수신 측에서 가용한 버퍼 공간이 얼마나 되는지 송신자에게 알려주는데 사용
- 연결의 각 측의 송신자는 별개의 수신 윈도를 유지

- 수신 윈도가 0일 경우 송신자 호스트는 차단되고 더는 데이터를 전송할 수 없으므로 이 문제를 해결하기 위해 송신 호스트가 1바이트 데이터로 세그먼트를 계속해서 전송하도록 요구

- UDP 의 경우 제공하지 않으므로 오버플로우, 세그먼트 분실
