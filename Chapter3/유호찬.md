# 3.1 트랜스포트 계층 서비스 및 개요

트랜스포트 계층 프로토콜은 각기 다른 호스트에서 동작하는 애플리케이션 프로세스 간의 논리적 통신을 제공한다.

송신 측 애플리케이션:메시지 → 트랜스포트:세그먼트 변환 → 네트워크:데이터그램 변환 → 수신 측 네트워크 :세그먼트 추출 → 트랜스포트:세그먼트 처리

위와 같은 단계를 거쳐서 애플리케이션 프로세스 간 통신을 한다.

### 트랜스포트 계층과 네트워크 계층 사이의 관계

트랜스포트 계층 : 다른 호스트에서 동작하는 프로세스들 사이의 논리적 통신

네트워크 계층 : 호스트들 사이의 논리적 통신

트랜스포트 계층 프로토콜은 종단 시스템에 존재하며 애플리케이션 프로세스에서 네트워크 계층까지만 메시지를 운반하고 그 이상은 영향을 미치지 못한다.

네트워크 계층 프로토콜이 지연 보장이나 대역폭 보장을 제공할 수 없다면 트랜스포트 계층 프로토콜은 프로세스끼리의 메시지에 대한 지연 보장이나 대역폭 보장을 제공할 수 없다.

그럼에도 특정 서비스(신뢰적인 데이터 전송, 보안)는 트랜스포트 프로토콜에 의해 제공될 수 있다. 

### 인터넷 트랜스포트 계층의 개요

트랜스포트 계층 프로토콜에는 UDP와 TCP가 있다.

UDP : 비신뢰적이고 비연결형

TCP : 신뢰적이고 연결지향형

개발자는 소켓을 생성할 때 둘 중 하나를 선택해야 한다. 

네트워크 계층 프로토콜은 인터넷 프로토콜(IP) 라는 이름을 가진다. 호스트들 간에 세그먼트를 전달하기 위해 최대한 노력하지만 어떤 보장도 하지 않는다.

전달을 보장하지 않고 순서대로 전달되는 것을 보장하지 않는다. 내부 데이터의 무결성 또한 보장하지 않으므로 비신뢰적 서비스라고 부른다.

각 호스트가 적어도 하나의 IP 주소를 가진다.

TCP와 UDP는 종단 시스템 사이의 IP 전달 서비스를 종단 시스템에서 동작하는 프로세스 간의 전달 서비스로 확장하는 것이다.

이를 트랜스포트 계층 다중화와 역다중화라고 부른다.

UDP는 프로세스간 데이터 전달과 오류 검출 두 가지 서비스를 제공한다.

TCP는 이에 더해 신뢰적인 데이터 전송, 혼잡 제어를 추가적으로 제공하여 더 복잡하다.

# 3.2 다중화와 역다중화

다중화와 역다중화를 수행할 때 각 프로세스의 소켓을 식별하기 위한 번호로 포트를 쓴다.

다중화 : 애플리케이션이 소켓으로 내보내는 데이터를 모아 헤더(포트번호)를 붙여 캡슐화하는 작업

역다중화 : 수신한 세그먼트에서 헤더(포트번호)를 확인하여 적절한 소켓으로 분배하는 작업

### 비연결형 다중와와 역다중화

UDP 데이터 전송에서 출발지와 목적지 포트번호로 세그먼트를 만들어서 전송하게 된다.

이때 목적지의 포트번호는 역다중화할 때 사용되며, 

출발지의 포트번호는 회신할 때 사용된다.

### 연결지향형 다중화와 역다중화

TCP의 경우 UDP와 다르게 4개의 요소(출발지의 IP주소 및 포트 번호, 목적지의 IP주소 및 포트 번호)에 의해 식별된다.

목적지의 포트 번호가 같더라도 출발지의 포트 번호가 다르다면 각각 다른 소켓으로 연결된다.

# 3.3 비연결형 트랜스포트: UDP

UDP는 트랜스포트 계층 프로토콜이 할 수 있는 최소 기능으로 동작한다.

다중화/역다중화 기능과 간단한 오류 검사 기능만 존재한다.

개발자가 TCP대신 UCP를 선택한다면 애플리케이션은 거의 IP와 직접 통신하는 셈이다.

TCP에 비해 UDP가 가진 장점은 다음과 같다.

1. TCP의 혼잡제어가 없으므로 데이터 손실을 감수하더라도 빠른속도로 데이터를 송신할 수 있다.
2. 연결 설정이 없어서 연결 지연이 없다
3. 연결 상태가 없어서 서버는 더 많은 클라이언트를 수용할 수 있다.
4. 작은 패킷 헤더 오버헤드를 가진다.

이러한 장점 때문에 각 애플리케이션마다 쓰이는 프로토콜이 다르다.

애플리케이션에서 신뢰성을 제공한다면 UDP 또한 신뢰적인 데이터 전송을 할 수 있다.(QUIC 프로토콜)

### UDP 세그먼트 구조

UDP 헤더에는 2바이트씩 구성된 4개의 필드를 가진다.

출발지, 목적지의 포트번호와 길이(헤더를 포함한 세그먼트 길이), 체크섬이다.

### UDP 체크섬

체크섬은 오류 검출을 위한 것이다.

출발지로부터 목적지로 이동했을 때 변경사항이 있는지 검사한다.

세그먼트 내의 16비트 합산에 1의 보수를 수행하여 나온 값을 통해 오류 검출을 한다.

UDP는 오류 검사를 제공하지만 오류를 회복하기 위해 어떤 일도 하지 않는다.

# 3.5 연결지향형 트랜스포트: TCP

### TCP 연결

TCP는 통신하는 두 프로세스가 서로 핸드셰이크를 하는 연결지향형이다.

또한 호스트A에서 B로 데이터가 흐른다면, B에서 A로도 갈 수 있는 전이중 서비스이고, 단일 송신자와 단일 수신자 사이의 점대점 연결이다. 여러 수신자에게 데이터를 보내는 멀티캐스팅은 불가하다.

TCP는 three-way handshake를 한다. 클라이언트가 먼저 연결을 원하는 세그먼트를 보내고 서버가 주 번째 세그먼트로 응답한다. 마지막으로 클라이언트가 세 번째 세그먼트로 응답하며 연결이 된다.

세그먼트에 담을 수 있는 최대 데이터 양은 MSS로 제한된다. 여기서 MSS는 헤더를 포함한 최대 크기가 아닌 애플리케이션 계층 데이터의 최대 크기이다. 따라서 최대 전송 단위인 MTU에 의해 헤더와 계산되어 MSS가 정해진다.

TCP 연결은 각 호스트에는 소켓 연결, 송신/수신버퍼, 변수의 집합으로 이루어진다.

### TCP 세그먼트 구조

크게 헤더 필드와 데이터 필드로 구성되어 있다.

데이터 필드에는 애플리케이션 데이터의 일정량을 담는다. 

헤더 필드에는 출발지 포트 번호, 목적지 포트 번소, 순서 번호, 확인응답 번호, 헤더 길이, 체크섬 등 다양한 필드가 존재한다.

- 순서 번호와 확인응답 번호
    
    TCP 세그먼트 헤더에서 가장 중요한 필드 두가지는 순서 번호 필드와 확인응답 번호 필드다.
    
    - 순서 번호
        
        전송되는 TCP 세그먼트 데이터의 첫 번째 바이트에 부여되는 고유 번호.
        
        수신 측이 분할 전송된 데이터를 재조립하고 누락을 판단하는 기준이 된다.
        
    - 확인응답 번호
        
        수신 측이 송신 측으로부터 다음에 수신하기를 기대하는 데이터의 바이트 번호.
        
        송신 측에게 데이터를 정상적으로 수신 했다는 신호이다.
        

### 왕복 시간(RTT) 예측과 타임아웃

TCP는 하나의 SampleRTT를 측정하여 평균값인 EstimatedRTT를 계산한다. 새로운 EstimatedRTT는 이전 값에 SampleRTT를 가중된 값을 더하여 갱신한다.

DevRTT는 SampleRTT가 EstimatedRTT로 부터 얼마나 벗어나는지에 대한 예측으로 정의한다.

그래서 타임아웃 값은 EstimatedRTT보다 크거나 같아야 한다. 너무 크거나 작으면 안되기 때문에 EstimatedRTT에 DevRTT값을 더한 값으로 사용하게 된다.

또한 타임 아웃이 발생할 때 타임아웃 값을 두 배로 설정하여 타임 아웃을 피하도록 한다. 다시 세그먼트를 수신하면 다시 계산하게 된다.

### 신뢰적인 데이터 전송

TCP는 IP의 비신뢰적인 최선형 서비스에서 신뢰적인 데이터 전송 서비스를 제공한다.

프로세스가 자신의 수신 버퍼로부터 읽은 데이터 스트림이 손상되지 않았으며 손실이나 중복이 없고, 순서가 유지된다는 것을 보장한다.

이 과정에 3가지 주요 이벤트가 존재한다.

1. TCP가 데이터를 IP로 넘길 때 타이머를 시작한다. 이 타이머는 앞에서 계산했던 타임아웃 값이다.
2. 타임아웃이 발생하면 해당 세그먼트를 재전송하고 타이머를 다시 시작한다.
3. 확인응답 세그먼트(ACK)를 수신하면 SendBase 변수를 갱신한다.

- GBN인가 SR인가?
    
    TCP는 GBN 형태의 프로토콜과 비슷하지만 차이점도 존재한다.
    
    TCP에서는 여러 세그먼트를 보낼때 모두 제대로 수신되었고 그 중에서 ACK 한 개가 손실되었더라도 해당 ACK에 대한 세그먼트가 재전송되거나 타임아웃전에 다음 ACK가 도착한다면 재전송되지 않지만 GBN은 그 이후 세그먼트들을 전부 재전송한다.
    
    TCP 수신자가 마지막으로 올바로 수신된 순서가 맞는 세그먼트에 대해 누적 확인응답을 하기보다는 순서가 틀린 세그먼트에 대해 선택적으로 확인응답을 하는 선택적 확인응답이다. 선택적 재전송과 결합했을 경우 SR 프로토콜과 유사하다.
    
    따라서 TCP는 GBN과 SR 프로토콜의 혼합으로 분류하는 것이 적당하다.
    

### 흐름 제어

TCP는 송신자가 수신자의 버퍼를 오버플로시키는 것을 방지하기 위해 애플리케이션에게 흐름 제어 서비스를 제공한다.

수신하는 애플리케이션이 읽는 속도와 송신자가 전송하는 속도를 같게 하는 것이다.

TCP 송신자는 IP 네트워크에서 혼잡 때문에 억제 될수 있다 - 혼잡 제어(congestion control)

흐름제어와 혼잡제어는 비슷하지만 명백하게 다른 목적으로 수행된다.

TCP는 송신자가 수신 윈도라는 변수를 유지하며 흐름 제어를 제공한다.

수신 윈도는 수신 측에서 가용한 버퍼 공간이 얼마나 되는지 송신자에게 알려주는 역할

TCP는 전이중이므로 각 측의 송신자는 별개의 수신 윈도를 유지한다.

세그먼트 윈도 필드에 수신 윈도를 이용하여 송신자에게 여유 공간을 지속적으로 알린다.

만약 여유 공간이 0이라면 더이상 전송하지 않으므로 여유 공간을 모르게 된다. 그래서 수신 윈도가 0일경우에 1바이트 데이터를 지속적으로 전송하여 확인하게 된다.

### TCP 연결 관리

<img width="702" height="633" alt="image" src="https://github.com/user-attachments/assets/2a75cec9-71ca-499d-b2ef-495a634fbe04" />

1. 클라이언트 측 TCP는 서버 측 TCP에게 SYN 비트와 최초의 순서 번호를 포함하여 세그먼트를 보낸다.
2. 서버측에 도착하면 서버측은 SYN 비트와 서버 최초 순서 번호, 클라이언트 순서 번호 + 1을 보낸다. SYNACK 세그먼트라고 불린다.
3. 2번의 연결 승인 세그먼트를 수신하면 클라이언트는 SYN 비트를 0으로 설정하고 서버 순서 번호 + 1하려 다시 세그먼트를 보내서 연결된다.

위 단계를 three-way handshake라고 부른다.

연결 종료할때는 아래와 같은 방식으로 종료된다.

<img width="626" height="693" alt="image" src="https://github.com/user-attachments/assets/c5eb626c-00ff-4a49-9ee1-2c37bcff189a" />

1. 연결 종료하려는 호스트 측에서 1로 설정된 FIN 비트를 헤더에 포함하여 보낸다. 
2. 서버가 수신하면 ACK 세그먼트를 보낸다.
3. 서버가 FIN 비트가 1로 설정된 종료 세그먼트를 보낸다.
4. 클라이언트가 수신하고 ACK 세그먼트를 보낸다.

이 과정을 통하여 연결 종료되며 할당된 자원이 해제된다.

클라이언트 TCP의 상태 전이

<img width="755" height="568" alt="image" src="https://github.com/user-attachments/assets/fb8885d9-0cd2-4e0e-a185-98edda97569d" />

SYN_SENT : 연결을 희망하는 SYN 세그먼트를 보낸 뒤 서버로부터 응답을 기다린다.

ESTABLISHED : 서버로부터 연결 확인응답을 수신하면 ACK를 보낸뒤 연결된다.

FIN_WAIT_2 : 서버로부터 ACK를 받고 서버의 FIN 비트를 포함한 세그먼트를 기다린다.

TIME_WAIT : 세그먼트를 받고 ACK를 보낸 뒤 대기 시간을 가지고 종료된다.

# TCP 혼잡제어

### 전통적인 TCP의 혼잡 제어

네트워크 혼잡에 따라 연결에 트래픽을 보내는 전송률을 각 송신자가 제한하도록 하는 것이다.

여기에 세가지 의문점이 있다.

1. TCP 송신자는 자신의 연결에 송신자 전송 트래픽 전송률을 어떻게 제한하는가?
    
    TCP 혼잡 제어 매커니즘은 추가적인 변수인 혼잡 윈도(cwnd)를 추적한다.
    
    확인 응답이 안된 데이터의 양은 cwnd와 rwnd의 최솟값을 초과하지 않는다.
    
    cwnd값을 조절하여 전송하는 속도를 조절할 수 있다.
    
2. TCP 송신자는 자신과 목적지 사이 경로의 혼잡을 어떻게 감지하는가?
    
    과도한 혼잡이 발생하여 경로에 있는 라우터 버퍼들이 오버플로되어 데이터 그램이 버려진다. 손실 이벤트가 발생하고 이를 인해서 경로상에 혼잡이 발생했음을 알게 된다.
    
    혼잡이 없는 경우 혼잡 윈도 크기를 증가시킨다. ACK가 빠르게 도착한다면 혼잡 윈도를 더 빠르게 증가시키고 느리게 도착한다면 느리게 증가시킨다.
    
3. 송신자는 종단 간의 혼잡을 감지함에 따라 송신율을 변화시키기 위해 어떤 알고리즘을 사용해야 하는가?
    
    TCP 송신자가 너무 빠르게 송신하면 혼잡 붕괴가 일어나고, 너무 느리게 송신하면 대역폭을 충분히 활용하지 못한다.
    
    - 손실된 세그먼트는 혼잡을 의미하며, 이에 따라 TCP 전송률은 한 세그먼트를 손실했을 때 줄여야 한다.
    - 확인응답된 세그먼트는 네트워크가 송신자의 세그먼트를 수신자에게 전송된다는 것이고, 이에 따라 이전에 확인응답되지 않은 세그먼트에 대해 ACK가 도착하면 송신자의 전송률은 증가할 수 있다.
    - 대역폭 탐색 : TCP 송신자는 혼잡이 발생하는 시점까지 전송률을 증가시키고 혼잡이 발생하면 다시 줄인다.

### TCP 혼잡 제어 알고리즘

1. 슬로 스타트(slow start)
    
    <img width="529" height="692" alt="image" src="https://github.com/user-attachments/assets/e1e75418-17af-405b-a487-a362126a28c8" />

    TCP 연결이 시작될 때 cwnd 값은 1 MSS로 초기화된다. 확인 응답을 받을 때 마다 1 MSS식 증가시킨다.
    
    손실 이벤트가 발생하면 cwnd 값을 1로 설정하고, ssthresh값을 cwnd/2로 정한다. 그리고 새로운 슬로 스타트를 시작한다.
    
    cwnd값이 ssthresh와 같으면 슬로 스타트는 종료되고 혼잡 회피 모드로 전환된다. 혼잡 회피 모드에서는 cwnd를 좀 더 조심스럽게 증사시킨다.
    
    3개의 중복 ACK가 검출되면 빠른 재전송을 수행한다.
    
2. 혼잡 회피
    
    cwnd값이 ssthresh를 도달 했을 때 1 MSS씩 선형적으로 증가시킨다. 
    
    3개의 중복 ACK 이벤트가 발생하면 덜 과감해야 하므로 cwnd값을 반으로 줄이고 ssthresh 값을 cwnd 값의 반으로 기록한다. 그 이후 빠른 회복 상태로 변경한다.
    
3. 빠른 회복
    
    cwnd 값을 손실된 세그먼트에 대해 수신된 모든 중복된 ACK에 대해 1 MSS만큼씩 증가시킨다.
    
    손실된 세그먼트에 대한 ACK가 도착하면 TCP는 혼잡 회피 상태로 들어간다.
    
    만약 타임아웃 이벤트가 발생한다면 빠른 회복은 슬로 스타트 및 혼잡 회피에서와 같은 동작을 수행한 후 슬로 스타트로 전이한다.
    
    초기 TCP 버전인 TCP 타호는 중복 ACK 손실이 발생하면 cwnd를 1 MSS로 줄이고 슬로 스타트 단계로 들어간다.
    
    새로운 TCP 버전인 TCP 리노는 빠른 회복을 채택한다.

    TCP 타호
    
    cwnd를 1로 줄이고 지수적으로 증가한다.
    
    TCP 리노
    
    cwnd를 9로 설정하고 선형적으로 증가한다.
    

### TCP 혼잡 제어: 복습

<img width="671" height="388" alt="image" src="https://github.com/user-attachments/assets/c8265d60-573f-4a0a-89d5-f482195308a5" />

TCP 혼잡제어는 RTT마다 1 MSS식 cwnd의 선형 증가와 중복 ACK 이벤트에서 cwnd의 절반화로 구성된다. 이러한 혼잡 제어를 AIMD 혼잡 제어라고 불린다.

사진과 같은 톱니 동작을 생기게 한다. 중복 ACK 이벤트가 발생할 때 까지 선형으로 증가하고 이벤트 발생 시 반으로 감소 시키지만 다시 선형으로 증가시키기 시작한다.

### TCP 큐빅

<img width="1280" height="830" alt="image" src="https://github.com/user-attachments/assets/9a8ea61d-aab6-4bda-b438-bea08b095223" />

이전 버전의 TCP는 최고 속도로 복구하는데 오래 걸리는 단점을 극복하기 위해 등장한 알고리즘

혼잡 손실이 발생하면 큐빅은 W_max까지 더 빠르게 증가한다. W_max에 가까워지면 대역폭을 조심스럽게 증가시킨다.

W_max를 넘어서도 손실이 발생하지 않는다면 기하급수적으로 빠르게 증가시킨다.
